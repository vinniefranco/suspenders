# The skill subsystem: disk-discovered SKILL.md skills, one always-loaded tool

Suspenders is a coding agent for small local models; its built-in tool set is small on purpose (ADR-0056). A *skill* is a way to teach the model a specialized capability without adding a tool: a directory containing a `SKILL.md` manifest whose markdown body is instruction text the model reads on demand. This ADR is the skill subsystem (P2c): how a directory of skill files becomes a catalog the model can browse and invoke, and what stays out. It is a faithful port of qwen v0.16.0's skill loader (`skills/skill-load.ts`, `skills/types.ts`, `tools/skill-utils.ts`, `tools/skill.ts`), adapted to Suspenders' conventions.

## Skills live on disk under `.suspenders/skills/`

A skill is a DIRECTORY, `<name>/`, containing a `SKILL.md` file. Skills are discovered from two roots: `<project-root>/.suspenders/skills/` (project) and `~/.suspenders/skills/` (the user's XDG config home, beside `config.json` and `themes/`). We use `.suspenders/` rather than qwen's `.qwen/`, matching every other Suspenders convention. A directory without a `SKILL.md`, and a plain file, are silently skipped (qwen's `loadSkillsFromDir`): each skill must be a directory with a manifest.

A `SKILL.md` is YAML frontmatter between `---` fences followed by a markdown body:

```
---
name: pdf
description: Work with PDF files
when_to_use: When the user asks to read or fill a PDF
---
Instructions the model reads when it invokes this skill...
```

`name` and `description` are REQUIRED; a manifest missing either (or with an empty value) is a parse error and the skill is skipped. `when_to_use` is optional and, when present, is appended to the description in the model-facing catalog. `name` must match qwen's `SKILL_NAME_PATTERN` charset (Unicode letters/digits plus `_ : . -`), so a name with a structurally-unsafe character (`<`, `>`, `/`, whitespace) is rejected at parse time - the name flows verbatim into the model-facing catalog, so rejecting the injection vector at the source is more reliable than escaping at every sink. Five further frontmatter keys drive behavior, each with its own section below: `paths`, `priority`, `disable-model-invocation`, `argument-hint`, and `hooks`. Two keys carry no behavior: `allowedTools` is informational only, and `model` is inert (both are covered under scope, below). A `SKILL.md` that carries none of these still loads off its `name` + `description`, so a minimal manifest is a valid skill.

## The frontmatter parser is hand-rolled, no YAML dep

We do not add a YAML crate. The landed fields (`name`, `description`, `when_to_use`) are flat `key: value` scalars, so `parse_skill_content` is a manual line scan mirroring qwen's regex `^---\n([\s\S]*?)\n---(?:\n|$)([\s\S]*)$`: normalize BOM + CRLF, split the leading `---` fence from the next `---`-only line (a `---` mid-value or mid-line does not close the block), then parse the frontmatter as flat `key: value` pairs and trim the body. A `key:` with no inline value and `- item` continuation lines (the list/nested shapes of the ignored fields) parse to nothing rather than crashing, and a single pair of surrounding quotes on a scalar is stripped. The split on the FIRST colon lets a value contain a colon (`Ratio 16:9`). This keeps the dependency surface flat; if a future field needs real YAML, that is a distinct decision.

## One always-loaded `skill` tool, the catalog IS the surfacing

There is ONE `skill` tool, not one tool per skill. It holds an `Arc<SkillManager>` (a stateful tool, like `McpTool`) and builds its description dynamically: the qwen scaffold (`Execute a skill within the main conversation` + `<skills_instructions>`) with an `<available_skills>` block spliced in, one `<skill><name/><description/><location/></skill>` entry per discovered skill (name + description XML-escaped via qwen's `escapeXml`, `when_to_use` appended to the description, `<location>` the skill's base directory). `<location>` carrying the skill's base directory is an intentional adaptation: qwen fills that slot with the level word (project/user/bundled), but the base directory is what a hook script or a follow-up read actually needs, so Suspenders surfaces the path instead. An empty catalog shows the "no skills configured" text, reworded to point at `.suspenders/skills/`.

That catalog IS the surfacing mechanism, so the tool is ALWAYS on the wire list the model sees (`always_load() == true`, never deferred). This is deliberately NOT the F3 deferred-tools path (ADR-0054): a deferred tool is hidden until `tool_search` reveals it, but the whole point of the skill tool is that the model reads the skill list off the tool's own description, so hiding the tool would hide the catalog. The `<available_skills>` block is analogous to how the Deferred Tools system-prompt section surfaces deferred tools - a name-and-description listing the model browses - except it rides the tool description rather than the system prompt. The tool is always registered (in `init_agent`), even with an empty catalog, so the model knows skills CAN exist.

Invoking the tool with `{skill: "<name>"}` returns that skill's body wrapped by `build_skill_llm_content` (VERBATIM from qwen: `Base directory for this skill: {baseDir}\nImportant: ALWAYS resolve absolute paths from this base directory when working with skills.\n\n{body}\n`), so the model gets the instructions plus the base directory for resolving any script/reference paths. The validate-empty message (`Parameter "skill" must be a non-empty string.`) and the not-found message (`Skill "{name}" not found. Available skills: {names}`) are qwen-verbatim.

## Fail-open discovery, mirroring MCP

`SkillManager::discover(project_root, user_root)` is a LEAF (it imports only `std` + `serde_json`, never agent/run/ui/session), the fail-open front the way `McpManager::connect` is for MCP. It walks each root's immediate subdirectories (sorted, so discovery order is stable), parses each `SKILL.md`, and records a `(skill <name>, reason)` failure for any manifest that fails to parse or validate - the skill is skipped, discovery carries on. An unreadable/absent root (the common no-`.suspenders/skills/` case) is a silent no-op. Project skills are walked before user skills, so on a name collision the project skill wins (qwen's project-over-user precedence); the shadowed user skill is dropped silently, not recorded as a failure.

The Agent runs discovery once in `init_agent` (beside the MCP attach) and surfaces each `failures()` entry as one `Event::extension_error("skill <name>", PreRun, reason)` launch notice - the same fail-open report line an MCP connect failure and an Extension crash take (ADR-0007). A broken `SKILL.md` is a visible skip, never a fatal.

## `paths:` conditional activation, hidden until a file is touched

A skill whose frontmatter carries `paths:` globs is a *conditional skill*: it is hidden from the model-facing `<available_skills>` catalog until a Tool Call touches a matching file path, and once matched it stays activated for the rest of the Session. This mirrors qwen's `skill-activation.ts` / `skill-paths.ts`. The `SkillManager` holds a skill-activation registry keyed by skill name; a plain skill (no `paths:`) is active from discovery, a conditional skill starts inactive. Activation is checked at the tool-scheduler seam AFTER a Tool Call succeeds: the just-run tool's touched path (the file argument it read or wrote) is matched against each inactive conditional skill's globs, reusing the existing `crate::glob_match` module rather than adding a matcher. On a match the skill flips to active, and the `skill` tool rebuilds its `<available_skills>` catalog on the next description read, so the newly-activated skill appears in the list the model browses. Reusing `glob_match` (already the engine behind the ignore-crate walk and `@path` completion) keeps one glob semantics across the codebase; checking activation on tool-call SUCCESS (not attempt) means a failed touch never leaks a hidden skill into the catalog.

## `priority`, parsed and stored, not a sort key

`priority` is an optional integer frontmatter field. It is parsed and stored on the skill, but it does NOT reorder the model-facing `<available_skills>` catalog or the `/`-menu listing: both stay name-sorted. qwen reserves `priority` for its `/skills` display layer, which Suspenders lacks, so there is no surface for priority to order and it stays a stored-but-inert hint. The value is parsed-and-normalized: a missing, empty, or non-integer `priority` is treated as `0` rather than failing the parse, so a malformed hint is non-fatal and the skill still loads.

## `disable-model-invocation` and user `/<name>` slash commands

Every discovered skill also registers as a dynamic slash command `/<name>`. Alongside ADR-0032's `&'static` array of command descriptors sits a *dynamic command-source layer*: the skill catalog contributes commands discovered at Session start, so `/pdf` sits in the same `/`-menu as `/model` and `/theme` but is sourced from disk rather than the static array. A normal skill is therefore BOTH a model-facing catalog entry (the model can call the `skill` tool with its name) AND a `/<name>` command the user can type. A skill with `disable-model-invocation: true` is dropped from the model-facing catalog and becomes `/<name>`-only: the user can trigger it, the model cannot see or call it. This is the escape hatch for a skill that is a user workflow rather than a model capability.

The two invocation paths are distinct on purpose. When the MODEL invokes a skill through the `skill` tool, that is the one path that registers the skill's session-scoped hooks (see the hooks section). When the USER types `/<name>`, the command injects `build_skill_llm_content(...)` (the same base-directory-wrapped body the tool returns) as a submitted user turn, mirroring qwen's `submit_prompt`: the instruction text enters the conversation as if the user had pasted it, which is a deliberately different path from the model calling the tool and does NOT register hooks. Keeping user invocation on the submit-a-turn path means a `/<name>` command needs no Agent round-trip to surface the skill body, and it composes with the ADR-0032 selector exactly like every other command.

## `argument-hint`, shown in the completion menu

`argument-hint` is an optional frontmatter string parsed and shown after the slash command name in the `/`-menu completion, so `/commit` can advertise `/commit <message>`. It is display-only: it annotates the command in the menu and never gates or parses the user's input. The user invocation injects `build_skill_llm_content(base_dir, body)` - the base-directory-wrapped skill body - as the submitted turn; the argument-hint is not consulted at commit and no separate arg string is spliced in (the fuzzy `/`-palette commits a highlighted command on the query-to-command boundary, so a fire-and-run skill has no trailing remainder to carry). The hint is purely a menu affordance advertising what to type into the ensuing turn.

## Bundled skills, a 4th level embedded at compile time

Beneath the project and user roots sits a third source, bundled skills, giving a precedence order of project > user > bundled. Bundled skills are qwen's shipped set, ported into Suspenders. Because Suspenders is a single self-contained binary (ADR-0019), a bundled `SKILL.md` cannot ship in a `dist/` directory the way qwen ships one; instead each bundled skill is embedded in the binary at compile time (via `include_str!`, no new dependency) and discovered from that embedded set, so there is no on-disk install step and no extra file to lose. Precedence resolves by name, exactly like the project-over-user rule but one level deeper: a project or user skill of the same name shadows the bundled one silently. Each bundled `SKILL.md` is audited so its body only references tools Suspenders actually has, because a bundled skill that told the model to call a qwen-only tool would be instruction text the model cannot act on.

The shipped bundled set is a deliberate subset of qwen's five. `batch` ports faithfully (its body is verbatim qwen except the one `task` tool reference, which Suspenders names `agent`). `stuck` is a Suspenders-native rewrite: it keeps qwen's purpose (diagnose a frozen or slow session) but grounds every instruction in Suspenders reality (a Rust binary named `suspenders`, `config.json` rather than `~/.qwen`, the linear JSONL session log of ADR-0010, and only the tools Suspenders actually has), because qwen's original body is welded to qwen's runtime sidecars and `~/.qwen` paths. Three of qwen's five are deliberately NOT shipped: `loop` is DEFERRED pending a real scheduling subsystem (its body is built entirely on `cron_*` tools Suspenders does not have, so shipping it would cite nonexistent tools); `review` and `qc-helper` depend on the `qwen review` CLI subcommands and the Qwen Code documentation tree respectively, neither of which exists here. A skill is only bundled when its every tool reference resolves in Suspenders.

## `hooks:`, session-scoped hooks registered on model invocation

A skill's `hooks:` frontmatter registers session-scoped Hooks at the moment the MODEL invokes the skill through the `skill` tool (not at discovery, and not on a user `/<name>` invocation), so a skill's hooks are live only once the model has actually loaded that skill. The skill's base directory is exported to hook commands as `SUSPENDERS_SKILL_ROOT` (qwen's `QWEN_SKILL_ROOT`, renamed to match every other Suspenders env), so a hook script can resolve paths relative to its own skill. The Hook subsystem itself, its lifecycle, event points, and execution model, is a separate design; see ADR-0066 for the full Hook subsystem. This ADR records only the wiring: a skill is one source of hooks, registered on model invocation, rooted at `SUSPENDERS_SKILL_ROOT`.

## Out of scope

Three qwen skill features are deliberately not supported, each for a reason rooted in how Suspenders is shaped:

- **`model` override** - not supported. In Suspenders a skill injects its instructions into the SAME conversation with no sub-run (the model reads the body and carries on), so there is no separate run to place on another model; the field has nothing to act on. Honoring it would also break ADR-0033, under which a Run runs on the Active Model, so a per-skill model would be a second, conflicting model authority. The field is semantically inert here and is parsed-and-ignored.
- **`allowedTools`** - informational only, parsed-and-ignored. It is retained so a real qwen `SKILL.md` still loads, but it gates nothing: qwen v1 does no tool-gating off this field either, so honoring it would invent a restriction qwen itself does not enforce.
- **Extension-level skills** - out of scope. Suspenders has no extension-install system to load skills FROM, and the "extensions" of ADR-0007 are an unrelated, retired concept, so there is no extension level to add. Bundled skills (above) cover the shipped-skill case that extension skills serve in qwen.
- **Command-merging (MCP prompts / file commands merged into the catalog)** - not applicable. qwen unifies other model-invocable command sources into `<available_skills>`, but Suspenders has no such source: there are no file-based prompt commands, and MCP prompts are not surfaced as commands (ADR-0056 discovers MCP tools only, not prompts). With nothing else to unify, the catalog is disk-plus-bundled skills only. Should a model-invocable command source ever land, it joins the catalog then.
